## Directory Structure

```
src/
  app/                  — App Router only. Pages are thin shells, no logic here.
  components/
    ui/                 — shadcn/ui generated components ONLY. Never edit these.
    layout/             — Header, Footer, Sidebar, ThemeToggle
    shared/             — reusable across features
    features/           — one subfolder per feature
  context/              — React context for light, non-complex state only
  hooks/                — all custom hooks, use-*.ts naming
  lib/                  — third party generated code (magicui, aceternity, etc).
                          Never manually edit or create files here.
  services/             — every API call lives here, never in components or hooks
  types/                — all TypeScript types and interfaces
  redux/                — heavy or complex global state only
    store.ts
    hooks.ts            — typed useAppDispatch and useAppSelector
    slices/             — one file per slice, [name]Slice.ts naming

public/
  images/               — raster images
  products/             — product images
  svgs/                 — SVG assets
```

### Directory Rules

- All code lives inside `src/`. No exceptions.
- `src/lib/` is owned by third party tools. Never create files here manually.
- `src/components/ui/` is owned by shadcn. Never edit files here.
- Pages in `src/app/` import from `components/`, `hooks/`, `services/`. No logic inline.
- When creating a new component, decide its home before creating:
  - Used only in one feature → `components/features/[feature]/`
  - Used across multiple features → `components/shared/`
  - Part of app shell → `components/layout/`
  - Generated by shadcn → `components/ui/`

## Imports

- Absolute imports everywhere. No relative imports (`../`, `./`).
- Always use path aliases:

```ts
import { Button } from "@/components/ui/button"
import { useDebounce } from "@/hooks/use-debounce"
import { api } from "@/services/base"
import type { User } from "@/types/user.types"
```

## Components

- One component per file. One named export per file.
- File name matches component name exactly. PascalCase.
- Props interface defined in the same file, named `[ComponentName]Props`.
- Keep components granular. If a component is doing too much, split it.
- No multiline comments inside component files. Keep code self-explanatory.
- No default exports except `page.tsx` and `layout.tsx` files.
- `"use client"` only when strictly required — hooks, browser APIs, event handlers.
- Server components by default everywhere else.

```tsx
// ✅ Correct
interface UserCardProps {
  name: string
  email: string
}

export function UserCard({ name, email }: UserCardProps) {
  return (...)
}

// ❌ Wrong
export default function UserCard(props: any) { ... }
```

## Styling

- Tailwind utility classes only. No inline `style={{}}`. No CSS modules.
- `cn()` for all conditional class merging. Import from `@/lib/utils` or wherever
  the project has it set up.
- `cva()` for components with 2 or more visual variants.
- Semantic color tokens only. Never hardcode colors.

```tsx
// ✅ Correct
<p className="text-foreground">
<div className="bg-background border border-border">
<span className="text-muted-foreground">
<button className="bg-primary text-primary-foreground">

// ❌ Wrong
<p className="text-gray-900">
<div className="bg-white border border-gray-200">
<p style={{ color: '#333' }}>
```

- Mobile-first always. Base styles first, then `md:` then `lg:`.
- Every component must be dark mode friendly. Every color class needs a `dark:` variant
  if it doesn't already adapt via CSS variables.

---

## Dark Mode

- Every component works in both light and dark mode without exception.
- Use CSS variable-based semantic tokens (they handle both modes automatically).
- When a color does not use a CSS variable, explicitly add a `dark:` class.
- `ThemeToggle.tsx` in `components/layout/` is the toggle. Never rebuild it elsewhere.
- Test every component mentally in both modes before considering it done.

## Animations

- framer-motion for all animations and transitions.
- No CSS transitions on interactive components — use framer-motion.
- Keep animations subtle and purposeful: duration 0.2s–0.4s, ease-out.
- Use `AnimatePresence` for mount/unmount transitions.
- Every page should have a subtle entry animation.
- Refer to `.agents/skills/framer-motion/SKILL.md` before adding any animation.

## State Management

### Use Context when:
- 1–2 small pieces of shared state
- Not frequently updated
- Scoped to a feature or small part of the app
- Place in `src/context/`, one file per context

### Use Redux Toolkit when:
- State is complex or deeply shared
- Multiple slices of related state
- Needs RTK Query for server state
- Follow this structure:

```
src/redux/
  store.ts          — configureStore, export RootState and AppDispatch
  hooks.ts          — typed useAppDispatch and useAppSelector, export both
  slices/
    authSlice.ts    — createSlice, export actions and reducer
    uiSlice.ts
```

- RTK Query for all server state when redux is already in use.
- Never mix RTK Query and the custom `api` object for the same resource.

## API and Services

- Never call `fetch()` directly in a component or hook.
- All API calls go through `src/services/` using the `api` object from `src/services/base.ts`.
- One service file per domain resource. Named `[resource].service.ts`.
- All service functions have explicit TypeScript return types.

```ts
// ✅ Correct
import { api } from "@/services/base"
import type { User } from "@/types/user.types"

export const userService = {
  getAll: () => api.get<User[]>("/users"),
  getById: (id: string) => api.get<User>(`/users/${id}`),
  create: (payload: CreateUserPayload) => api.post<User>("/users", payload),
}

// ❌ Wrong
const res = await fetch("/api/users")
const data = await res.json()
```

## TypeScript

- No `any`. Ever. Use `unknown` and narrow it.
- All types and interfaces live in `src/types/`.
- File naming: `[resource].types.ts`.
- Prefer `interface` for object shapes, `type` for unions and primitives.
- All API response shapes typed in `src/types/api.types.ts`.

---

## Error Handling

- No `console.error()` or `console.log()` in production code.
- All errors surfaced to the user via the custom toast component.
- Wrap async service calls in try/catch and toast the error message.

```ts
// ✅ Correct
try {
  const user = await userService.getById(id)
} catch (error) {
  toast.error(error as string)
}

// ❌ Wrong
console.error(error)
```

## Loading States

- Skeleton screens for all loading states. No spinners.
- Every data-fetching component has a skeleton variant.
- Match skeleton dimensions as closely as possible to the real content.
- Use shadcn's `Skeleton` component from `components/ui/skeleton`.

## Icons

- lucide-react only. No heroicons, no react-icons, no inline SVGs unless
  the asset is in `public/svgs/` and used as an `<Image />`.
- Always pass `size` and `className`:

```tsx
<Search size={20} className="text-muted-foreground" />
```

## What Not To Do

- Do not edit `src/components/ui/`. Shadcn-managed.
- Do not edit `src/lib/`. Third party-managed.
- Do not use inline `style={{}}`. Tailwind only.
- Do not hardcode colors. Semantic tokens only.
- Do not use relative imports. Absolute only.
- Do not use default exports except `page.tsx` and `layout.tsx`.
- Do not add `console.log` or `console.error`. Toast errors instead.
- Do not use spinners for loading. Skeletons only.
- Do not use react-icons or heroicons. lucide-react only.
- Do not call `fetch()` in components or hooks. Services only.
- Do not add CSS transitions on interactive elements. framer-motion only.
- Do not rebuild `ThemeToggle`. It already exists in `components/layout/`.
- Do not create files in `src/lib/` manually.
- Do not add `"use client"` unless absolutely forced to.
